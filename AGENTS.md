# AGENTS.md — SRAF Agent Operations Guide

> This file is for AI coding agents (Claude Code, Cursor, etc.) working
> on this repository. Read this BEFORE making any changes.

## What this project is

SRAF (Sales Resource Allocation Framework): an allocation-intelligence
layer for FMCG distributor territory management. World model +
evidence-governed knowledge base + reasoning that proposes to humans.

Spec baseline: `docs/00–08` v1.2.1 FROZEN. Implementation design:
`DESIGN.md` (living doc). Ontology corrections: D1–D13 in DESIGN.md §5.

## MANDATORY WORKFLOW (do not skip steps)

For any change that affects the data model, geometry pipeline, or
business semantics:

```text
Step 1  RESEARCH    Search standards (ISO/OGC/GB-T), academic papers,
                    and existing implementations. Write a research brief
                    (like analysis/research_brief_four_bounds.md).
                    Present findings to the business owner.

Step 2  CONFIRM     Business owner confirms:
                    - the direction is correct
                    - the scope is acceptable
                    - domain assumptions are validated
                    DO NOT proceed without explicit confirmation.

Step 3  DESIGN      Write a design document (like docs/D14_*.md):
                    - Problem statement with evidence
                    - Root cause analysis
                    - Corrected ontology / data model
                    - Impact analysis (files that change / must not break)
                    - Validation plan
                    - Rollback plan

Step 4  REVIEW      Business owner reviews the design document.
                    Address feedback. Do not implement until approved.

Step 5  IMPLEMENT   Write code following the approved design.
                    Run validation gates (§7 of the design doc).

Step 6  VERIFY      End-to-end verification:
                    - ref_check.py (145 §refs resolve)
                    - consistency_check.py (83/83)
                    - unittest (13 pass)
                    - browser verification for UI changes

Step 7  DOCUMENT    Update CHANGELOG, DESIGN.md ADR, knowledge_base/
                    if the change is ontological. Commit + push.

For minor fixes (typo, comment, CSS): skip steps 1–4, go straight to
implement + verify + commit.
```

### Why this workflow exists

In this project, jumping straight to implementation caused:
- a CRS mixing bug that made four-bounds verification unreliable for weeks
- a single-contiguity ontology assumption that silently dropped territory
  components
- an over-engineered polygon surgery pipeline that had to be deleted

All three were caught by the business owner, not by tests. The workflow
above exists to prevent this pattern.

## DOMAIN CORRECTIONS (hard-won, do not regress)

| # | Correction | ADR / KB |
|---|---|---|
| D11 | **Area-first semantics**: decision object = sub-area of a territory. Store attribution is a derived effect. Editing stores directly is a CRM job. | K-PRIN-006 |
| D11 | **Logical fence merge**: no polygon surgery (union/difference). Territory fence = convex hull of the dealer's stores (derived view). Transfer = store reassignment only. | |
| D12 | **Rules-first, LLM fallback**: deterministic rules <1s handle standard commands; LLM only for free-form text. `@`-mention engine guarantees LLM sees full legal names. | |
| D13 | **CRS boundary normalization**: data packs are GCJ-02 (Amap system). Load: GCJ→WGS once (`pack_from_disk`). Write: WGS→GCJ (`pack_for_disk`). Internal geometry = pure WGS-84. Mixing systems = ~623m systematic offset (measured in Guangzhou). | |
| D14 | **Multi-component territory**: a dealer's territory MAY comprise multiple disconnected spatial components. Continuity is a business preference, not an ontological constraint. | K-PRIN-007 |

### Things that are TRUE (do not argue)

- The dealer fences in `data/gz/region.json` are **customer-drawn original
  data** (GCJ-02, hand-traced along roads/rivers, median 1271 vertices).
  They are NOT generated by our four-bounds pipeline.
- The contract four-bounds text was reverse-extracted FROM those fences
  (see `analysis/CONTRACT_PACK_guangzhou.md`).
- **Store distribution is NOT ground truth** for fence geometry validation.
  A store can legitimately be outside a fence (OOF). Use pure geometry
  for geometric benchmarks.
- Our four-bounds rebuild pipeline currently has poor fidelity
  (oracle IoU median 0.069, barrier component median 0.153, V1c closed
  median 0.493). This is measured and documented — do not claim it works
  without running `tools/bench_rebuild.py` and `tools/bench_oracle_ladder.py`.

## DATA CONTRACT

| Rule | Detail |
|---|---|
| CRS | Data packs default GCJ-02 (Amap). `meta.crs` field is declarative. Born-WGS packs (frontend-created) declare `WGS84`. |
| Normalization | Load: `pack_from_disk` (GCJ→WGS). Write: `pack_for_disk` (WGS→GCJ). Internal: pure WGS-84. |
| **NO DATA FILES IN GIT** | `data/*` and `analysis/*` are `.gitignore`d. Business data (store coords, contract terms, dealer names in bulk) must never be committed. Only schema docs (`data/README.md`) are tracked. |
| **NO KEYS IN GIT** | API keys live in `~/.claude/settings.json` (LLM) and `~/.sraf/vision.json` (vision). Never hardcode, never commit. |
| **NO STORES AS TRUTH** | Store positions are business output, not geographic ground truth. Never use store PIP to validate fence geometry. |

## KNOWLEDGE BASE RULES

1. Every entry MUST have `source` — no provenance, no entry.
2. `confidence: MEDIUM/LOW` entries only support secondary reasoning.
3. Data entries (FACT/BENCH) refresh with snapshots; principle entries
   (PRIN) require business-owner confirmation to modify.

## CODE CONVENTIONS

- Server: pure stdlib (`http.server`, `json`, `urllib`). No Flask/FastAPI.
- Geometry: shapely. But avoid polygon surgery (union/difference) —
  use logical merge (D11) instead.
- LLM: accessed via Anthropic-compatible proxy (`~/.claude/settings.json`
  env). Model default `MiniMax-M3` (`SRAF_LLM_MODEL` to override).
  Rules path must succeed without LLM.
- Frontend: Leaflet + vanilla JS, single file (`tools/demo_page.html`).
  UI text is Chinese (business users); documentation is English.
- Error messages shown to business users: Chinese.
- Code comments: English preferred; Chinese acceptable if referencing
  Chinese domain terms.
- Version: bump `DESIGN.md` status (v0.6 → v0.7 etc.) for ontological
  changes; bump `docs/CHANGELOG_v1.2.*` for spec-adjacent changes.

## VALIDATION GATES (run before any commit)

```bash
python3 tools/ref_check.py          # 145 §refs resolve
python3 tools/consistency_check.py  # 83/83 pass
python3 -m unittest discover tests -q  # 13 pass
```

For geometry/pipeline changes also run:

```bash
python3 tools/bench_rebuild.py      # rebuild fidelity benchmark
python3 tools/bench_oracle_ladder.py  # oracle-ladder decomposition
```

For UI changes: open in browser (headless or relay), verify all panes
render, no console errors, layer toggles work.
