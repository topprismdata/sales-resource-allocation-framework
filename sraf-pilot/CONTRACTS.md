### 3.5 冻结规则（v1.1 新增，回应 L1 冻结点②③④⑤；L2 不得自行选择）

#### 3.5.1 街道 ↔ 区县连接

**`街道.父级id` == `区县.区域编码`，精确等值匹配。禁止模糊/名称匹配。**

- 已取证：174 个街道的 `父级id` 取值集合 100% ⊆ 11 个区县编码集合
- 试点区街道数：海珠(440105) **18** 个、荔湾(440103) **22** 个，合计 **40** 个
- 出现 `父级id` 不在区县编码集合中的街道 → **抛错**，不得静默跳过

#### 3.5.2 围栏归属试点区的判定

```
overlap_ratio = clamp(area(fence ∩ (海珠 ∪ 荔湾)) / area(fence), 0.0, 1.0)
```

**判定顺序（v1.2 修正，L2 于 T-103 指出 v1.1 存在区间重叠缺陷）：**

```
① 灰区检测优先：若 0.2 <= overlap_ratio <= 0.8  → [ESCALATION]，停止，不得自行取舍
② 否则入选判定：overlap_ratio >= 0.5           → 入选
③ 否则                                          → 排除（须在 data_issues.md 留档）
```

> **为何灰区优先**：0.2~0.8 是**双峰假设失效的警报**，不是普通的边界情况。
> 阈值 0.5 之所以安全，前提正是「实测分布双峰、中间零样本」。一旦出现中间值，
> 说明数据性质变了，此时任何自动判定都不可信 —— 必须人看。
>
> v1.1 缺陷：「≥0.5 入选」与「0.2~0.8 须 ESCALATION」在 **[0.5, 0.8] 重叠**，
> ratio=0.6 既算入选又算灰区。v1.2 用显式判定顺序消除歧义。
> 边界值 0.5 落在灰区闭区间内，按①处理（ESCALATION），**不入选**。

- 已取证：分布**双峰、灰区为零**（经销商 15 条相交中 0.2~0.8 区间 **0 条**；
  业代 21 条相交中同样 **0 条**），故阈值取 0.5 安全
- `overlap_ratio` 必须写入 fence schema 供追溯
- **浮点钳制**：交集/自面积数学上 ≤1，浮点舍入实测出现过 `1.0000000000000016`，
  必须 `clamp` 回 `[0, 1]`
- 预期结果（P1 实测已验证）：经销商 **4 条**入选（ratio 全为 1.0000）、
  业代 **17 条**入选（ratio 0.9969~1.0000）

#### 3.5.3 主键与重复名

- **`src_id` = CSV 的 `片区id` 字段原值**（已验证两份 CSV 内均唯一）

#### 3.5.4 坐标系验证方法（全部参数冻结）

| 项 | 冻结值 |
|---|---|
| 样本 | 试点区内**全部**经销商围栏（n=4，不抽样） |
| 顶点抽样 | 每条围栏顶点等距抽样**至多 200 点** |
| 距离函数 | 复用 `intelligence.world.haversine_km`，**禁止自写经纬度换算** |
| 坐标转换 | 复用 `intelligence.coords.gcj2wgs`，**禁止另写转换公式** |
| 对照 A（共配准检验） | 围栏顶点**原坐标** → 最近单元边界，取距离中位数 |
| 对照 B（参考量，**不作判据**） | 围栏顶点经 `gcj2wgs` 转换后 → 最近单元边界，取距离中位数 |
| 对照 C（转换自检） | `gcj2wgs` 在这批顶点上的**位移量**中位数 |
| 不变量 | **单元几何一律保持原样，三组对照中都不转换** |

**判定式（v1.3 修正）：**

```
median_A < 1.0 m   （共配准：顶点级重合）
    AND
500 m <= median_C <= 750 m   （转换自检：位移量符合 D13 广州 ~623 m）
    → verdict = SAME_CRS_GCJ02
否则 → verdict = INCONCLUSIVE，写 [ESCALATION]，不得下结论
```

> ### ⚠️ v1.2 的方法学错误（L2 于 T-104 指出，L0 确认）
>
> v1.2 判据为 `A < 100 m 且 B > 300 m`。**`B > 300 m` 在本试点结构上不可达。**
>
> **原因：「到最近边界的距离」是饱和度量。** 在密集网格中，无论把点位移多远
> （623 m 或 10 km），它到*最近*边界的距离都不会超过约半个格子。实测：
>
> | 量 | 值 |
> |---|---|
> | `gcj2wgs` 真实位移量 | **623.2 m**（与 D13 记录吻合，转换函数正常） |
> | 单元面积中位数 | 0.322 km² → 等效边长 **567 m** |
> | 最近边界距离的**理论上限** ≈ 半格 | **284 m** |
> | 实测 median_B | 118~237 m（与半格距同量级，印证饱和） |
>
> 阈值 300 m 落在 284 m 天花板之上 → **永远达不到**。这是 L0 的设计错误。
>
> **修正逻辑**：真正的判据是 A 的**绝对量级**，不是 B。
> `median_A = 0.0016 m`（1.6 毫米）远低于任何饱和下限——两套独立生产的数据
> 不可能偶然重合到毫米级，只可能是**顶点共享**（客户围栏就是照着这套路网单元描的）。
> 转换自检 C 则独立确认 `gcj2wgs` 确实生效且量级符合 D13，排除「转换没跑」的可能。
>
> B 保留为记录性指标（有助于后续诊断网格密度），**但不再参与判定**。

 "median_A_m":0.0,        // 判据①：< 1.0
 "median_B_m":0.0,        // 记录性，不判定
 "median_C_disp_m":0.0,   // 判据②：500~750

### 3.6 Oracle 单元集与表达能力指标（v1.4 新增，回应 L1 于 P2 拆卡的 ESCALATION）

> **背景**：v1.3 的 `oracle_unitsets.json` schema 只声明 `coverage: float`，
> **未定义公式**。而主线 `docs/basic_units_comparison.md` 已明确记载：
>
> > 覆盖率检验**已废弃**（单元铺满全城时对任意多边形都 100%，空洞）
>
> 单元是**铺满**试点区的，所以「围栏被单元覆盖了多少」对任何多边形都趋近 100%，
> 这个指标不含信息。**字段名 `coverage` 本身就是陷阱源，v1.4 起废弃该名。**

#### 3.6.1 Oracle 单元集的选取（冻结）

```python
U(F) = { u : fence_geom(F).covers(centroid(u)) }
```

- 判定用 **`covers`**（含边界），非 `contains`。理由：确定性优先；
  质心恰落在围栏边界是零测度退化情形
- 必须额外统计并落盘 `boundary_centroids`（质心恰在边界上的单元数）。
  **正常应为 0**；若 > 0 须在 JOURNAL 记录，但不阻断

#### 3.6.2 指标定义（冻结）

设 `U = unary_union(选中单元)`，`F = 围栏几何`：

| 字段 | 公式 | 用途 |
|---|---|---|
| **`iou`** | `area(U ∩ F) / area(U ∪ F)` | **G2-b / G2-c 的唯一判据** |
| `recall` | `area(U ∩ F) / area(F)` | 诊断：围栏有多少被单元并集覆盖 |
| `precision` | `area(U ∩ F) / area(U)` | 诊断：单元并集有多少溢出围栏外 |
| `straddle` | `count( 0.2 <= area(u ∩ F)/area(u) <= 0.8 )` | 骑跨单元数：围栏切穿单元的程度 |

- `straddle` 用**闭区间** `[0.2, 0.8]`，与 §3.5.2 灰区约定一致
- `recall`/`precision` **仅作诊断，不参与门禁**。作用是解释「为什么 iou 低」：
  recall 低 = 漏选；precision 低 = 多选溢出
- **禁止把 `recall` 当成绩报**——那正是被废弃的 coverage 换个名字

#### 3.6.3 `oracle_unitsets.json` schema（替换 §3.3 旧定义）

```jsonc
{"method":"3.6-v1.4",
 "link_min_m":50,
 "boundary_centroids":0,
 "fences":{
   "<src_id>":{"name":"...","layer":"dealer"|"yeidai",
               "unit_ids":[int,...],          // 升序唯一，值域 0..223
               "iou":0.0, "recall":0.0, "precision":0.0,
               "straddle":0, "components":1}  // components = 邻接图连通分量数（D-9）
 }}
```

#### 3.6.4 门禁判据（更新 §5）

| 门禁 | 判据 |
|---|---|
| **G2-b** 业代 n=17 | **`median(iou) >= 0.95`** |
| **G2-c** 经销商 n=4 | **无阈值**，逐条报 `src_id / iou / recall / precision / straddle / components`；**任一条 `iou < 0.90` → 触发 P2b** |

### 3.7 粒度分层（v1.5 新增，来自 P2b 实验的实测发现）

试点确认存在**两个粒度层**，分工明确、不可混用：

| 层 | 内容 | 规模（试点区） | 面积中位 | 用途 |
|---|---|---|---|---|
| **L1 业务层** | 官方四级路网单元（带区/街道属性） | 224 | 0.3216 km² | **DSL 定址、多块领地计数、对外陈述** |
| **L2 路网层** | OSM 全等级线网 polygonize 细面 | 10,071 | 0.0028 km²（细 113×） | 表达能力上限、精细化调整 |

#### ⚠️ `components` 必须在 L1 层报告

实测（P2b，2026-08-30）：

| 围栏 | L1 官方单元 | L2 细面 |
|---|---|---|
| 穗穗盛 | **2** | 22 |
| 禧璟 | **1** | 10 |
| 华新 | **1** | 6 |

细面粒度下，面与面的邻接判定被拓扑碎片污染，数出来的是**几何伪影**，
不是业务上真实的"不相连地盘"。

**裁定**：D-9 的多块领地计数 `components` **只在 L1 层计算与对外陈述**；
L2 层的 components 仅作内部诊断，**禁止出现在任何报告或 demo 中**。

#### P2b 实验结论（已完成，不再触发）

浩盛以 L1 单元 `iou=0.8382`（`recall=0.8408` = 漏选）触发 P2b；
改用 L2 细面后 **`iou=0.9500`（`recall=0.9607`）**，四条经销商全部 ≥0.95，
**触发解除**。同时业代 `median(iou)` 由 0.9691 略降至 0.9635（仍达标）。

→ 在试点尺度复现了主线「两种画围栏的语言」结论，支持 **L1/L2 双粒度层级库**。

#### P3 的定址层

**P3 的筛选 DSL 定址 L1 层**（官方单元）。理由：
`in_street` / `in_district` 依赖单元自带的街道/区县属性，L2 细面不具备；
且业务语言天然是"哪几个街道"，不是"哪几千个路网面"。
L2 细面留作后续精细化调整的可选能力，**不阻塞 P3/P4**。

### 4.1 定位

- **LLM 只输出这棵树，绝不输出任何坐标。** 几何一律由确定性执行器计算。
  （对齐主线 D12：规则优先、LLM 兜底）
- 树是**可序列化 JSON**，可存档、可 diff、可人工审阅修改。
- 求值结果是**单元 id 集合**（`set[int]`），不是多边形。

### 4.2 原语（P3-MVP：前 4 个；P3b：后 2 个）

#### P3-MVP（零外部依赖，只用官方街道/区县数据）

```jsonc
// 1. 某街道内的单元
{"op": "in_street", "name": "南石头街道"}

// 2. 某区县内的单元
{"op": "in_district", "name": "海珠区"}

// 3. 并集（★ 多块领地由此天然产生）
{"op": "union", "args": [ <node>, <node>, ... ]}

// 4. 差集
{"op": "minus", "args": [ <node>, <node> ]}   // args[0] - args[1]
```

#### P5（原 P3b，v1.8 由「条件触发」提升为正式阶段）

```jsonc
// 5. 某线要素某一侧的单元（scope 限定搜索范围，省略则为全试点区）
{"op": "side_of", "line": "华南快速", "dir": "东",
 "scope": <node|null>}
// ⚠️ dir 必须支持【八方位】：北 南 东 西 东北 东南 西北 西南
//    v1.7 只写了四方位 —— P5 快速实验实测四方位 0.6765 / 八方位 0.7931，
//    差 0.12，斜向不可省。见 §4.5

// 6. 中心点周边（兜底）
{"op": "near", "center": [lon, lat], "radius_km": 3.0}
```

### 4.3 求值语义（执行器必须严格遵守）

| 原语 | 判定规则 |
|---|---|
| `in_street` | 单元 `street` 属性**等于**解析后的街道名 → 入选。（v1.7 修正，理由见下）|
| `in_district` | 单元 `district_code` 等于该区编码 → 入选。（用属性，不做几何判定）|
| `union` | 各子节点结果集的并 |
| `minus` | `eval(args[0]) - eval(args[1])` |
| `side_of` | 单元质心相对该线**最近点的局部切线**的有向侧（不是整线走向）；`scope` 先缩小候选 |
| `near` | 单元质心到 `center` 的球面距离 ≤ `radius_km` |

**名称解析**：街道/区县名支持「精确 → 去后缀（街道/镇/区）→ 包含匹配」三级容错。
匹配到 0 个或 >1 个 → **抛错，不得静默取第一个**。
（主线 `lookup_geometry` 的两字前缀兜底是已知隐患，试点禁止复刻。）

> ### ⚠️ v1.7 修正：`in_street` 由几何判定改为属性判定（G3 于 T-304 暴露）
>
> **v1.6 及以前**：`in_street` = 单元质心落在街道多边形内（几何）。
> 但 `in_district` 用的是属性（`district_code` 相等）—— **同类问题两套判据，
> 这是 L0 的设计不一致。**
>
> **实测后果**（海珠+荔湾 224 单元）：
>
> | | 几何语义 | 属性语义 |
> |---|---|---|
> | 与属性不符的单元 | **10 / 224（4.5%）** | — |
> | 质心不落在任何街道内 → **DSL 永远选不到** | **uid=43** | 无 |
> | `union(全部 40 街道)` 覆盖率 | **223/224 ❌ 不完备** | **224/224 ✅** |
> | 与 `in_district` 一致 | ❌ | ✅ |
>
> **典型案例 uid=214**：面积 2.59 km²，横跨琶洲街道 56.6% / 官洲街道 43.4%
> —— 是**骑跨单元**。厂商在 `street` 属性里定为「官洲街道」，
> 质心却落在琶洲一侧。
> **街道归属是业务事实，不该被质心启发式覆盖。**
>
> **裁定：`in_street` 改用 `street` 属性精确相等**，与 `in_district` 统一。
> 街道多边形几何**只用于名称解析**（把用户文本映射到规范街道名），
> **不参与单元选取**。
>
> 三条依据，按权重排序：
> 1. **完备性**：属性语义下 `union(全部街道) == 全部单元`，几何语义下有单元
>    永远不可达 —— 不可达单元会让"围栏 = 单元集合"这个本体出现盲区
> 2. **内部一致性**：与 `in_district` 用同一类判据
> 3. **业务正确性**：骑跨单元的归属是厂商在数据里做的业务决策，
>    不应被几何启发式改写
>
> **T-304 的失败是契约缺陷被正确捕获，不是实现错误。**
> L2 忠实实现了冻结的（错的）语义；L1 选的独立期望值来源（raw `street` 字段）
> 反而编码了更正确的语义。G3「必须 100% 精确」的高标准正是为此设立。

### 4.4 输出契约

```jsonc
{
  "unit_ids": [12, 13, 40, 41, 77],
  "components": 2,              // 邻接图连通分量数（D-9：只报告，不干预）
  "area_km2": 31.7,
  "rule": { /* 原样回填求值用的 DSL 树，供追溯 */ },
  "warnings": []   // ⚠️ v1.6 澄清：见下
}
```

> **v1.6 澄清 `warnings` 的语义**（L2 于 T-303 实现时暴露的措辞不一致）：
> v1.5 的示例写了 `["街道『XX』匹配到 0 个单元"]`，但 §4.3 明确规定
> **名称匹配 0 个或 >1 个一律抛错**。两处冲突。
>
> **裁定：抛错优先。** 名称解析失败走 `DslError` 异常，
> **绝不降级为 warning 后返回一个残缺结果** —— 那正是主线
> `lookup_geometry` 静默认错地标的失败模式。
> `warnings` 保留为将来非致命提示的插槽，当前实现恒为 `[]`。

### 4.5 P5 快速实验结论（2026-08-30，L0 oracle 天花板实验）

**结论：`side_of` 值得实现。中位 Jaccard 0.5000 → 0.7931（+0.2931），
达标数 2/21 → 10/21。**

| 方案 | 中位 J | Δ | ≥0.8 |
|---|---|---|---|
| 街道列表（P4 现状） | 0.5000 | — | 2/21 |
| +丢弃 | 0.5000 | +0.0000 | 5/21 |
| +**四**方位 | 0.6765 | +0.1765 | 6/21 |
| **+八方位** | **0.7931** | **+0.2931** | **10/21** |

独立佐证：主线于同日测得 街道级 0.62 → 街道+方向 **0.78**。
两条独立路径、不同语料、不同实现，落在同一位置。

#### 由实验直接得出的三条实现约束（冻结）

**① `dir` 必须支持八方位**
四方位 0.6765 vs 八方位 0.7931，差 0.12。v1.7 只定义了四个，**已修正**。

**② 表达式组装必须约束「至少保留一项」**
实验中 `海珠荔湾11`（2 个真值单元，分散在两个街道各占 6.7%/10%）出现
**Jaccard 0.0800 → 0.0000**：贪心打分对所有选项均为负 → 全部丢弃 → 空集。
**这是启发式缺陷，不是 side_of 的结论。** 正式实现**必须**约束结果非空。

**③ `side_of` 解决不了「街道的 6.7%」级别的小片区**
实测最小街道占比 <10% 的围栏（海珠荔湾10/11/02、特渠0103 等），
**半个街道仍然太大**。这类需要**路级切分**或**更细的原子**（见 §3.7 的 L2 层）。
→ P5 与 P6（细面迁移）**互补，不是二选一**。

#### 实验的已知限制
方位近似用「街道质心切半」，而真正的 `side_of` 沿**具体道路**切、分辨率更高。
**故 0.7931 是下界，真实天花板应更高。**
